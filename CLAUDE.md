# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Built on the Meta Model API (Muse Spark, SAM 3.1, Muse Image). A server with a good connection does the work and sends the result to someone who can only receive text. A router (`evac/router.py`) lets Muse pick tools for any message; underneath are four modes: **emergency** (alert + GPS → instructions and a text map), **photo** (a photo that won't load → description + the outline of its main subject), **weather radar** (latest radar + 2-hour forecast as text) and **directions abroad** (walking route on street data, re-sent as the person moves). Every map draws only what the reply is about (`evac/focus.py`). Each reply exists in four versions: SMS aligned for **iPhone Messages** (iPhone only, multi-part SMS is fine), a 58-column monospace map for WhatsApp, a small picture (400 px WebP) and a full JPEG.

## Commands

There is no build, lint or test suite. Python 3.12 in `.venv` (`python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt`; git-ignored): `requests`, `pillow`, `numpy`, `fontTools` (font checks) and `meta-sam-parser` (Meta's SAM 3.1 parser, needs Python ≥ 3.10; the old Anaconda 3.9 can't run it). Run everything with `.venv/bin/python` (the simulator's launch config does).

```bash
python3 main.py --ask "Is it going to rain on my walk to the Colosseum?" --at 41.9010,12.5016 -v  # router
python3 main.py samples/palisades_fire.txt --at 34.0445,-118.5300 -v   # wildfire, raster map
python3 main.py samples/nyc_fire.txt --at 40.75491,-73.97441 -v        # Manhattan street-grid map
python3 main.py samples/nyc_gas_leak.txt --at 40.7560,-73.9740 -v      # street (not avenue) closure
python3 main.py samples/nyc_fire.txt --at 40.75491,-73.97441 --laptop 58  # + the WhatsApp map
python3 main.py --photo some.jpg                                          # photo mode
python3 main.py --radar 40.7128,-74.0060                                  # radar mode (live data)
python3 main.py --walk "Castelo de São Jorge, Lisbon" --at 38.7139,-9.1406 -v
python3 main.py --walk "Colosseum, Rome" --from "Pantheon, Rome" --at 41.9010,12.5016   # named start instead of GPS
python3 sim/server.py                                                     # simulator on :8765 (.claude/launch.json: "simulator")
```

`-v` prints the parsed alert (`notice (llm)` vs `notice (regex)` shows whether Muse ran), the distance check, closures found, and `text map: ... worst row drift X cells`. Drift must stay at or below ~0.07 cells (the 🔴 marker costs 0.04, one `Λ` 0.063; two `Λ` in a row are never allowed); that line is the regression check for the map.

`.env` (git-ignored, loaded by `evac/llm.py`) holds `LLAMA_API_KEY` (a Meta Model API key; `MODEL_API_KEY` also works). Optional: `LLM_BASE_URL` (default `https://api.meta.ai/v1`), `LLM_MODEL` (default `muse-spark-1.3`), `LLM_REASONING_EFFORT` (default `minimal`). With no key, everything falls back to regex parsing and a message template.

## Architecture

Request flow: `router.handle(message, you, image)` → Muse (`llm.chat_tools`) picks tools from `tools.schemas()` → `tools.call` runs them in parallel (never raises; errors go back to the model) → each tool returns a short JSON summary to the model and keeps its bulky result in `ctx.store[tool name]` → Muse writes the reply → `router._versions` turns the kept results into the versions (emergency reply > walking route > radar > photo). Emergencies always go through `emergency_reply` (= `pipeline.run`) and its text is used verbatim. Without a key, `_run_rules` routes on keywords.

**Scene and renderers:** `evac/scene.py:Scene` is what to draw (you, view centre and size, text, roads, closures, zone, goal, route as lat/lon, aerial + masks, walk, street_grid, banner, `focus`, `marks`). `evac/render.py` draws a Scene as `sms` (textmap), `mono` (laptopmap), `small`/`picture` (imagemap). Renderers never fetch or route; every version draws `scene.route`. The emergency and directions modes build Scenes; radar and photo still render their own versions (next step: a raster layer in Scene). When changing a renderer, compare outputs with the model off (`llm._key = lambda: None`) against a saved baseline: SMS and pictures should stay byte-identical unless the change is meant to alter them.

`evac/pipeline.py:run` is the emergency flow: `notice.parse` → `geo.current_location` → `locate` (incident) → distance check (far = one line, return) → `grid.Grid` sized to the zone → aerial tiles + `segment` → `osm.fetch_roads` → `add_roads` (closures) → `add_hazard_circle` → `route` → `textmap.render_grid` or `render_raster` → `instructions` (Muse rewrite) → `compose`; with `laptop=N` it also calls `laptopmap.render` (N columns) and with `image=True` `imagemap.render`. `evac/photo.py`, `evac/radar.py` and `evac/directions.py` are the other modes; each returns `sms`, `text`, `mono` (+ bytes/gzip) and, except photo, `image`. `sim/server.py` exposes them as `/api/alert|photo|radar|directions` and the page renders every result with one `triple()` function.

**Focus (only what matters):** `evac/focus.py:select(scene)` sets `scene.focus`, the roads the maps draw; renderers read `scene.shown`. It keeps the roads walked (the *nearest* road to 2+ route points, within a distance scaled to the route's point spacing; "every road within 14 m" kept 75 roads in old Lisbon), the biggest named cross street at each turn, main roads crossed (walking) or all rank ≥ 3 in view (alerts), every closed road, and the destination's street (plus yours for alerts). `select(scene, minimal=True)` (one walking step) keeps only the walked streets and the turn's cross street, clipped to a fifth of the view's half-width around the route (a square mapped as one closed way would otherwise be drawn all round). A focused SMS map draws only those and the zone's edge; the WhatsApp map adds step numbers and ★ landmarks, shades the zone as edge ░ + worst part ▓, drops trees and empty rows; the picture draws the rest as faint grey context. `focus.fit` frames a view around points with a margin of 15% of what it shows (no fixed zoom). `pipeline.run` focuses every alert scene and starts the text with `lead()` ("GO EAST NOW toward ...") when the person is inside the zone.

**Walking is a Trip, one step at a time:** `directions.run(user, destination, start=None)` starts from a named place if given (the `walking_route` tool's `start`; "walk from the Pantheon to the Colosseum" used to route from GPS). `plan` downloads the streets once and, in the background, landmarks (`osm.fetch_landmarks`: churches, monuments, stations, pharmacies, cafés; waited for at most `LANDMARK_WAIT_S` after the streets, then cached for next time). The fine grid targets 8 m cells (160-480 columns, ~2 s to route at 480); steps come from it (`Grid.legs`, where an unnamed sidewalk takes its street's name). Each message is only the current step, to the next intersection, and the turn there, with the most notable landmark at the turn and one beside the step (`directions.step`, `landmarks`). Its map is fitted to you, that step, a third of it past the turn (15-80 m) and the landmarks. `move(trip, you)` (templates, ~1 s): arrived; same street with > 80 m to go (one line, no SMS/WhatsApp map); else the next step with its map. `along`/`astray` simulate walking or a wrong turn for the simulator (`/api/directions/move`, trips kept in `sim/server.py:TRIPS`).

**Photo outlines (one object):** Muse's description names the main object as a short noun phrase (`object`); `photo.sam_object` asks SAM 3.1 for it (retrying with the last word), takes the biggest confident match, and works on its box + 12% margin at the full 240-column working resolution. The shape is SAM's mask; without Meta's parser, `subject_mask`/`single_object` (the colour method: background = colours making up ≥ 15% of the border, Otsu threshold, close gaps, biggest piece, holes filled) run inside that box, with the box's ellipse as a last resort. No match: the colour method on the whole photo (`find_object`). `contour` traces the result with marching squares in `─ │ ╭ ╮ ╯ ╰` (one cell in Menlo), 58 columns; SMS gets a 24-column `#` silhouette with figure-space blanks. The result says `shape_from`. Test pictures: `sim/samples/` (made with Muse Image, `muse-image-1.0` on `/images/generations`) and the HEIC account pictures in `/Library/User Pictures`.

**Checked drawing (WhatsApp only; `evac/sketch.py`):** Muse's description also lists `things` (up to 5 objects, main first, no backgrounds). `sketch.find` asks SAM for each in parallel (biggest confident match; a thing under 30% of the photo's width and height is segmented again on a crop around it; masks over 35% of the photo are dropped as backgrounds unless it's the main thing). `compose` crops the full-size masks to all of them, then draws every outline into one 58-column drawing (earlier things on top) with a number inside each and a key. `check` renders the drawing without numbers as a PNG in Menlo and asks Muse, fresh and without the caption, what it can make out (as raw text Muse recognised 1 of 6 outlines, as an image 4 of 6), then a text-only call matches that against the list. Repair, up to 3 attempts: drop what wasn't recognised; if nothing was, draw the main thing alone. The attempt with the most recognised things (then the fewest things) is sent, with "(Muse, shown only this drawing, recognised: …)". `photo.run` returns `things`, `check` and `attempts`. SMS is unchanged (the single-object silhouette). A photo takes ~7-16 s this way. Object shapes combine both: `sketch.refine` keeps the unblurred colour-contrast pixels (`_sharp_colour`) inside a grown SAM mask plus SAM's eroded core, only if that overlaps SAM's mask by IoU ≥ `AGREE` (0.85; the bicycle and flamingo fell below it when colour pulled in the wall and water); it works on the crop at ≤ 480 px (full-size filters once took 6 minutes). A main object under `TINY` (3%) of the photo is drawn as the whole scene (`background`: brightness bands in light lines; objects heavy `━┃┏┓┗┛` or solid `█`) plus a close-up. Muse also gives a broad `category` that SAM tries when the name fails ("fortune cookie" → "food"). Every Muse JSON reply is defensive: `llm.chat_json` only returns dicts, `sketch.check` turns failures into "not recognised", and `photo.run` falls back to the single-object drawing if the loop raises.

**SAM 3.1 (`evac/sam.py`):** model `sam-3.1` is served on `/v1/responses` (chat completions refuses it). Send one user message with `input_text` (a noun phrase) and `input_image`, `metadata` `mask_encoding: one_bit`, `include_confidence: "true"` (strings). Output text: `<0f>` then records `id<|box;x1;y1;x2;y2;w;h;c|><|mask;x=0;y=0;c;data=H,W,<enc><payload>|>`; boxes are in the sent image's pixels, corners inclusive; the mask is box-sized. The payload is compressed and the SAM License forbids reverse-engineering it: parse and decode only with Meta's `meta-sam-parser` (`image_segmentation_format().create_parser()`, `push(text)`, `finish(CompletedOutcome()).result.records`: box and mask records by `object_id`; `decode_mask_to_raster(record.mask)` gives row-major 0/1 bytes for the record's half-open `bounds`). Responses are cached in `cache/sam/` by image and prompt.

**Aerial terrain:** `segment.segment(img, "auto")` uses SAM 3.1 for water only (it outlines the sea cleanly but finds almost no trees or buildings from above) and the colour heuristic for the rest. Alerts use it; walking maps pass `"color"` (they draw no terrain) so steps make no extra SAM call.

Things that span files and are easy to break:

- **The model copies, code computes.** `notice.SCHEMA_PROMPT` asks Muse for numbers, units and street names exactly as written (`{"value": 2, "unit": "mi"}`, `avoid_roads: [{road, from, to}]`); `notice._normalize` converts to `zone_radius_m` and segment dicts. Letting the model convert made the radius differ run to run, which changed the map bbox and missed the road cache.
- **Muse Spark reasons before answering** and those tokens count toward `max_completion_tokens`. At default effort it spent 1,500 to 2,000 reasoning tokens (5 to 10 s) per small extraction; `minimal` gives the same answers in 1 to 2 s. An empty `content` with `finish_reason=length` means the limit was eaten by reasoning.
- **Overpass is the slow, flaky part** (30 s to 2 min, timeouts). `osm._overpass` sends a new query to every mirror at once (first answer wins, 40 s each) and caches it by an MD5 of the exact query in `cache/osm/`, so any change to bbox maths invalidates the cache. `osm.fetch_roads` also keeps `cache/osm/index.json` of the areas it holds and cuts a covered area from an earlier download instead of fetching it (an alert's map area is usually inside its intersection lookup's). An alert waits at most `pipeline.ROADS_WAIT_S` (15 s) for its map's streets, then routes on imagery and lets the download finish in the background for the next reply. The intersection lookup is not cut short (a wrong incident location is worse than a slow one); it searches around the geocoder's hit and then around the reader, because a missed "A and B" geocode falls back to the middle of avenue A.
- **Street names are matched through `osm.norm_road`** ("5 Av" = "5th Avenue" = "Fifth Avenue", "W 47 St" = "East 47th Street"; directions and ordinals are dropped). Closures, intersections and the Manhattan grid all depend on it.
- **Intersections are found in road data, not the geocoder.** `pipeline.locate` splits "A and B", fetches roads around the rough geocode (or the user) and calls `osm.find_intersection`. Nominatim placed "5 Av and W 47 St" ~600 m off and returned nothing for Lexington & 51st.
- **Zone sizing:** no radius in the alert means a 150 m point incident (`DEFAULT_RADIUS_M`); the map half-width scales with the radius, so city incidents get ~25 to 65 m cells and wildfires ~600 m text cells. The "X m from you" wording uses distance to the incident for small zones and to the zone edge for large ones.
- **Three renderers share one route.** `textmap` (SMS), `laptopmap` (monospace) and `imagemap` (JPEG) all draw `scene.route` over `scene.shown`, centred on `scene.center or scene.you`; a scene with no zone is plain directions (goal = destination). Directions draws a 160-column route; its steps come from the 40-column grid (`Grid.legs` gives each step's start for `marks`).
- **Overpass helpers:** `osm._overpass` caches every query; `fetch_places` (radar town labels) gets one quick try and `radar` skips it for 10 minutes after a timeout. `WALKABLE` excludes service roads and trail paths because big-city queries timed out with them.
- **Radar colours → rain:** RainViewer's free tiles (max zoom 7) have a fixed colour scheme; `radar.PALETTE` maps colours back to dBZ from RainViewer's published colour table. It has no forecast frames, so the 2-hour timeline comes from Open-Meteo.
- **`grid.Grid`** is a north-up raster in local metres with cell height = 2 × width (monospace aspect); routing is Dijkstra with per-cell costs (roads cheap, closures 60, cost multiplied deeper inside the hazard). It is used for routing and for the raster map, but not for the Manhattan map.

## Text maps (`evac/textmap.py`)

Messages renders texts in SF Pro (proportional). Only characters measured to be exactly one digit wide at 17 pt may repeat in a row: `= # + < > 0 $ ¤ £ ¥ ×` and U+2007 FIGURE SPACE as the blank. Narrow glyphs are padded to that width with thin/hair spaces (`TOKENS`: `v`, `|`); slightly wide ones (`Λ` +6%, `S` +1.2%) are allowed only once or twice per row and are listed in `DRIFT`. The "you" marker is the 🔴 emoji (17 px), padded to exactly two cells; `_place_you` gives it the next cell (`skip`). Small misalignment (a pixel or two) is acceptable; a whole cell is not. When adding a symbol, measure it first (browser canvas with `font: 17px system-ui`; `-apple-system` silently falls back to Times in Chrome) and add any width error to `DRIFT`.

- Words go only at the end of rows (street names) or in the legend, never inside the grid. Labels that would make a row exceed `BUBBLE_PT` are dropped, because a wrapped row destroys the map.
- `render_grid` is used when the incident is named at a Manhattan intersection (`is_grid_place`). It rotates coordinates by `GRID_BEARING` (29°), takes each avenue's/street's median position from OSM, and places everything by interpolation; avenue order comes from the hard-coded `AVENUES` list.
- Messages are UCS-2 (67 characters per SMS part); current replies are 9 to 12 parts.
- Alignment has only been checked in SF Pro on a Mac, not on a real iPhone.

## Monospace maps (`evac/laptopmap.py`, WhatsApp)

WhatsApp shows ```text``` in monospace but can't colour it. Only glyphs measured one cell wide in Menlo/Monaco/Courier are used: box drawing (`─━│┃┼╋╱╲╳`), shading (`░▒▓█`), arrows, `◆ ⌂ × ≈ ·`. Braille is avoided (falls back to a wider font on Mac). The 🔴 "you" is 1.66 cells in Menlo and takes two cells, leaving its row ~1/3 cell short. 58 columns is the widest that fits the simulated WhatsApp bubble (65% of the pane) without wrapping; narrow maps get a taller aspect. Manhattan is rotated 29° so avenues run up; street names are written on the street line, avenue names in a header. Unfocused scenes drop side streets above 25 m per character unless walking, and footpaths are routed on but not drawn; focused scenes draw exactly `scene.focus`.

## Conventions

- Every commit updates `README.md` with what the program does, how it works, and example inputs/outputs copied from real runs (re-run the samples; don't hand-write outputs). The commit message describes the same.
- NYC sample alerts are fictional drills and are labelled as such inside the alert text.
- Model and network failures always fall back (regex parse, template message, imagery-only routing) instead of blocking the reply.
